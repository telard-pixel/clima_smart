# Clima Smart 1.0.1 release design

## Goal

Publish the current adaptive controller as a coherent GitHub and HACS release,
while fixing the known one-shot vane retry defect, bringing the documentation in
line with the code, and adding automatic verification for future pushes.

## Scope

The release will contain four related changes only:

1. Change the integration version from `0.19.0` to `1.0.1`. Version `1.0.1` is
   required because GitHub already has a `1.0.0` release whose manifest contains
   `0.16.0`; publishing `0.19.0` would move backwards under semantic version
   comparison.
2. Make the daytime vane restoration one-shot only after both requested select
   operations succeed or require no operation. A failed or unsupported vane
   command must remain eligible for another evaluation during the same wind-down
   window.
3. Update the README so its description matches the two-mode adaptive controller,
   current defaults, 15-minute sleep boost, current entities and version.
4. Add a small GitHub Actions workflow that checks Python syntax, JSON files and
   the complete standalone regression suite on pushes and pull requests.

No climate thresholds, fan bands, schedules, adaptive-target formulas, defaults,
entity identifiers or live Home Assistant settings will be changed by this
release.

## Vane retry behavior

`_compute()` currently sets `_vane_restored_on` before `_apply_select()` has sent
anything. The marker will move out of the decision path. The desired vane
positions will still be computed during `PHASE_WIND_DOWN`, but the controller will
mark the date complete only after the apply phase establishes that both configured
vanes are already correct or were changed successfully.

The apply result must distinguish three outcomes:

- no entity or no desired position: no work is required for that axis;
- entity already at the requested position, or a successful service call: that
  axis is complete;
- missing/unavailable entity, unsupported option, refusal backoff or failed
  service call: that axis is incomplete and must remain retryable.

The one-shot marker is set only when every requested axis is complete. Manual vane
changes after a successful restoration remain respected for the rest of the day.

## Testing

Development follows a red-green cycle:

1. Add a regression test proving that a failed daytime vane service call leaves
   restoration pending and a later evaluation retries it.
2. Confirm the new test fails against the current implementation for the expected
   reason.
3. Implement the minimum controller change.
4. Confirm the new test and all existing tests pass.

Before publication, run the same checks locally that CI will run:

- `python3 -m compileall -q .`
- JSON parsing for `manifest.json`, `hacs.json`, `translations/en.json` and
  `translations/it.json`
- `python3 -m unittest -v test_regressions.py`

## GitHub publication

Work will stay on `agent/release-1.0.1`. Only the design, regression fix, version,
documentation and workflow files will be committed. The branch will be pushed and
opened as a pull request against `main`. After the checks pass, the pull request
will be merged. Tag `1.0.1` and the GitHub release will be created from the exact
merge commit on `main`, and the release metadata will be re-read to verify the tag,
manifest version and published status.

No existing tag or release will be deleted or rewritten.

## Post-release live analysis

After publication, Home Assistant will be inspected in read-only mode. The review
will collect the installed Clima Smart version, config entry/options, linked entity
states, diagnostic sensors, climate attributes, outdoor and indoor temperature,
humidity, house-average inputs, auxiliary switches and relevant recent logs.

Suggestions for improved comfort will be based on those observed values and on
the controller's actual decisions. Proposed behavior changes will be kept separate
from this release and will require their own approval before implementation.
